Replay of recorded measurements · golden live run, 17 Aug 2026

Same GPU. Same model. Same work. One config costs 68.5% less per token.

Throttle measured two vLLM settings on one NVIDIA A100 80GB PCIe, six times in counterbalanced order, and verified the difference. It does not make the GPU faster. It tells you, with a confidence interval, which setting is cheaper and by how much.

Read this first. The baseline, max_num_seqs=1, is deliberately simple: one sequence at a time, so no batching, far below vLLM’s default. This was a first real-GPU test, not a typical production gain. Results apply to this model, engine, GPU and workload only.

Arithmetic at this measured rate

Same tokens, about a third of the GPU-hours.

Against a deliberately simple max_num_seqs=1 baseline (no batching). Not a typical production gain.

Pick a monthly volume of output tokens. GPU cost = tokens ÷ 1,000,000 × the measured $/M for each config.

Assumes the GPU is kept busy at the tested load. A dedicated GPU is billed per hour whether busy or idle, so savings appear only if you run fewer GPU-hours. Your model, prompts, load and GPU change $/M, which is why Throttle measures your stack instead of quoting ours.

How you get this on your stack

throttle check before and after each change.

Three checks to measure your noise, change one setting, check again. Throttle prints $/M tokens with a 95% interval and CHEAPER, MORE EXPENSIVE or NO WINNER, and says NOT CALIBRATED until it has enough repeats. For a decision-grade A/B, throttle golden runs the six-position protocol shown above.

# 1. current config, 3 runs (noise)
$ for i in 1 2 3; do
    throttle check --url http://localhost:8000 \
      --model Qwen/Qwen2.5-0.5B-Instruct \
      --gpu-hourly-rate 1.39 --label before
  done
# 2. restart with --max-num-seqs 8
$ throttle check --url http://localhost:8000 \
    --model Qwen/Qwen2.5-0.5B-Instruct \
    --gpu-hourly-rate 1.39 --label after \
    --config max_num_seqs=8 --monthly-tokens 1B
