Your second GPU might be costing you 28% more per token

Qwen2.5-72B on rented AMD MI300X: one GPU cost $1.67 per million output tokens, two GPUs with tensor parallelism cost $2.14. 1.56x the throughput, 28% more per token. The run, the arithmetic, and when a second GPU is still worth it.

Kushagra KanaujiaFounder, ThrottleOct 19, 20265 min read

I gave a 72B model a second GPU. It got 1.56x faster. Every benchmark dashboard would call that a win.

It also made every token 28% more expensive.

Qwen2.5-72B-Instruct, vLLM GPU $/hr Output tokens/s $/M output tokens
1x MI300X (TP1) $2.99 498 $1.67
2x MI300X (--tensor-parallel-size 2) $5.98 777 $2.14

Throughput went up 1.56x. The bill went up 2x. You pay the difference on every token you serve. This post is the run behind those numbers, why it happens, and when a second GPU is still the right call.

The setup

I rented an AMD MI300X VM from Hot Aisle and served Qwen/Qwen2.5-72B-Instruct in BF16 on vLLM (ROCm build 0.23.1). An MI300X has 192 GB of memory, so the 72B fits on one card. That matters: it means the second GPU is a choice, not a requirement.

  • Config A: one GPU, vLLM defaults.
  • Config B: the same weights on two GPUs with --tensor-parallel-size 2. Nothing else changed.
  • Workload: Throttle's default check: 5 blocks of 32 requests, 32 concurrent, max 256 output tokens, temperature 0, cold prompt cache (every request is tagged so the prefix cache can't make later runs look cheaper).
  • Price: Hot Aisle's on-demand list price, $2.99 per GPU-hour. That's an ASSUMED rate, not an invoice, so two GPUs are $5.98/hr.

I checked the one-GPU config four times in a row before changing anything, so I knew the run-to-run noise first. Then three checks of the two-GPU config.

The raw numbers

Config Checks ($/M output tokens) Avg seconds per block
1 GPU $1.671, $1.670, $1.664, $1.664 12.70 s
2 GPUs $2.143, $2.138, $2.132 8.14 s

Every block produced about the same number of output tokens on both configs: 6,311 to 6,345 per 32 requests. So the only things that moved the price were time and the hourly rate. Two GPUs finished a block in 8.14 seconds instead of 12.70. That's the 1.56x. But they cost twice as much per second.

2.00x the price ÷ 1.56x the speed = 1.28x the cost per token

The result held in 3 of 3 checks: +28.1% to +28.8%, against a run-to-run noise bound of 0.8%. This isn't noise. It's arithmetic.

The answers didn't change either. A fixed 6-prompt sample at temperature 0 came back identical on 5 of 6 prompts; the sixth differed in wording only. Same tokens, same answers, more dollars.

Why speed charts miss it

Tokens per second and latency are what every serving benchmark reports, and both look better on two GPUs. Neither one knows what a GPU-hour costs. Tensor parallelism splits each layer across cards, and the cards have to talk to each other on every forward pass. You get more speed, but not 2x more, and the gap is what you pay for.

If you only watch tokens per second, you can scale your way into a bigger bill and call it an upgrade.

My own tool got this wrong first

Here's the honest part. Throttle 0.5.1, the version I ran this with, printed CHEAPER for the two-GPU config. Its verdict rescaled the candidate to the baseline's GPU rate, so it compared speed at the same price and quietly dropped the second card from the bill.

That's exactly the mistake this post is about, and I made it in code. Since 0.6.0, throttle check --gpus 2 counts the extra GPU as a real config change and prints MORE EXPENSIVE. The numbers above are judged in real dollars: two GPUs at two GPUs' price.

When a second GPU is still the right call

This isn't "never use tensor parallelism." It's "know what you're buying."

  • The model doesn't fit on one card. Then TP2 isn't an option, it's the floor. The question becomes which multi-GPU layout is cheapest, and that's worth measuring too.
  • You have a latency target one GPU can't meet. If users need tokens faster than one card can produce them at your traffic, paying more per token can be the right trade. Make it a decision with a dollar figure attached, not a side effect of a benchmark.
  • Your traffic is different from mine. I measured one workload: 32 concurrent requests, short prompts, 256-token answers. Longer contexts, bigger batches or a different GPU can move the ratio. That's why you measure your own instead of borrowing mine.

What I'd avoid is the default reflex: "it's slow, add a GPU." Before you do, price both configs in dollars per million tokens on your own traffic.

How to check yours

# baseline: 1 GPU, three times, to measure your noise
throttle check --url http://localhost:8000 --model Qwen/Qwen2.5-72B-Instruct \
  --gpu-hourly-rate 2.99 --gpus 1 --label tp1

# restart vLLM with --tensor-parallel-size 2, then:
throttle check --url http://localhost:8000 --model Qwen/Qwen2.5-72B-Instruct \
  --gpu-hourly-rate 2.99 --gpus 2 --label tp2

--gpu-hourly-rate is the price of one GPU; --gpus multiplies it. Throttle says CHEAPER or MORE EXPENSIVE only when the change beats the noise it measured on your box, and NO WINNER otherwise. More on the cost-per-GPU trade-off in the guide vLLM tensor parallel size: cost on 1 vs 2 GPUs.

Caveats

One model, one engine, one workload, one session, on rented MI300X at list price. The $2.99/hr is an input, not a bill.
