We built Autotune: find the cheapest serving config that still gives the same answers

Autotune searches serving configs on your own GPUs and keeps the cheapest one that beats the noise, prices every GPU it uses, and rejects configs whose outputs changed. How it works, what it costs, and what "same answers" does and doesn't mean.

Kushagra KanaujiaFounder, ThrottleOct 27, 20266 min read

Two of my own runs on rented MI300X GPUs taught me the two ways a config search goes wrong.

  • A second GPU made a 72B model 1.56x faster and 28% more expensive per token. A search that optimizes speed picks it.
  • vLLM's on-the-fly FP8 made the same model look 47% cheaper, but the answers changed shape, and on the 32B it answered "!!!!". A search that optimizes dollars alone picks that.

So I built a search that can't make either mistake. It's called Autotune, and it's shipping in Throttle 0.7.0 as part of Throttle Cloud. This post is how it works and what it does not do.

What it does

You give Autotune three things: how to launch your server, which settings to try, and what one GPU costs per hour.

throttle autotune --url http://localhost:8000 --model Qwen/Qwen2.5-7B-Instruct \
    --gpu-hourly-rate 2.49 --concurrency 16 --monthly-tokens 2B \
    --launch "vllm serve {model} --tensor-parallel-size {tp} --max-num-seqs {seqs} --gpu-memory-utilization {mem}" \
    --space tp=1,2 seqs=64,128,256 mem=0.85,0.9

For each trial it starts the server with one config, waits until it answers, measures it in dollars per million tokens exactly like throttle check, and stops the server. At the end it prints the cheapest config that passed, the cost per million tokens before and after, what that's worth per month at your token volume, and a launch command you can paste.

How it decides

  1. Baseline first, three times. Trial 0 is your current config, measured three times on one server start. That gives a run-to-run noise bound for your box before anything is compared.
  2. Only a verified CHEAPER counts. A candidate wins only if its cost change is bigger than that noise bound, the 95% confidence intervals don't overlap, and its outputs didn't change. Anything else is not a win, however good the headline number looks.
  3. GPU count is priced. --gpu-hourly-rate is the price of one GPU. Each trial pays for the GPUs it uses, read from tp / tensor_parallel_size (or --gpus-param). Two GPUs that are 1.56x faster are still 28% more per token, and Autotune sees that.
  4. OUTPUT CHANGED is rejected. At temperature 0 the same prompts should get the same answers. If a config makes answers more than 10% longer or shorter, or many more hit max_tokens, it's thrown out, even when it's the cheapest thing in the table.
  5. Greedy, one setting at a time. It walks one setting up or down from the best config so far while each step is a verified CHEAPER that also beats the best cost, and stops a direction at the first step that isn't. It ends when a full pass finds nothing better or at --max-trials (8 by default).

The point isn't to find the fastest config. It's to find the cheapest one you can trust.

What "same answers" means, exactly

The title says "still gives the same answers," and I want to be precise about it. Autotune's output check compares answer length and how many answers hit the token cap, at temperature 0, against the baseline. It does not grade content. It catches breakage that changes shape, like a model that pads to the cap or spits out "!!!!". It will not catch a model that gives a wrong answer of the right length.

So treat Autotune's pick as a shortlist of one, then run your own evals on it before production. Quantization changes in particular deserve a real eval.

What a run looks like (simulated)

I don't have Autotune results from real hardware to show you yet, so here's the built-in dry run. Every number below is SIMULATED: a made-up speed model, no GPU, nothing charged. It's here to show the shape of the output, not a result.

throttle autotune --dry-run --monthly-tokens 2B

Every number above is SIMULATED (--dry-run): a made-up speed model, not your server.

Read it for the logic, not the dollars. The simulated FP8 trial is the cheapest row in the table and gets rejected because its output changed. The two-GPU trial is priced at two GPUs, so it loses to the one-GPU winner. Those are the two lessons from the MI300X runs, written into the search.

What it costs to run

Autotune is a Throttle Cloud feature. Each trial is metered at $1.00 of credits, the baseline included, and is charged before it runs. If you run out of credits mid-search, it stops cleanly before the next trial and still prints the best config found so far; nothing more is charged. New Cloud accounts start with $10 of credits and no card. --dry-run is free, needs no GPU and no login.

A few safety rails, because it restarts your server: it refuses to start if something is already answering at the health URL, it stops the whole process group after each trial, and the most expensive trial is checked against your safety limits before anything runs. Launch commands, endpoint URLs and logs stay on your machine; only configs, costs and verdicts are sent to your account. The details are in docs/cloud.md.

Why this is the paid part

The free CLI shows you where the money goes. Autotune is how it comes back: it turns "we should probably tune this" into one config with a verified dollar figure attached. For teams with a real GPU bill, we run the same search with you in a 2-month pilot: free for the two months, and afterwards you pay a share of the savings we verify together. No savings, no bill.

Status

Autotune is in Throttle 0.7.0, which ships together with Throttle Cloud. Until then you can read the code (src/throttle/autotune.py) and run the dry run from source. No one outside the project has run it on their GPUs yet. When there are real results, they'll be posted here with the raw records, the same way as every other number on this blog.
